A `jwks_uri` supplied via <<openid-authorization-code, Open ID Connect>> metadata is registered as a signature configuration for request tokens only when `micronaut.security.authentication` is set to `idtoken`.

IMPORTANT: The remote JWK Set is retrieved with the JDK `HttpURLConnection`, and redirects are never followed. A redirect to another address is treated as a failure to load the JWK Set. See <<providerHttpClient, HTTP Clients for the Provider>>.

**Failure back-off**

If a remote JWK Set cannot be retrieved (for example, the connection is refused, the endpoint responds with a non-2xx status or the body cannot be parsed) or the retrieved JWK Set contains no keys, the JWK Set is not requested again until a back-off elapses. While the back-off lasts, tokens which cannot be verified by another signature configuration are rejected without contacting the JWKS endpoint. This prevents an unauthenticated client from triggering one outbound JWKS request (and one error log entry) per request while the authorization server is unavailable. The back-off is keyed by JWKS url. You can configure its duration with:

[configuration]
----
micronaut:
  security:
    token:
      jwt:
        signatures:
          jwks-client:
            failure-backoff: 10s
            retrieval-timeout: 30s
----

`failure-backoff` defaults to 10 seconds. Set it to `0s` to disable the back-off and retry the retrieval for every token.

`retrieval-timeout` (default 30 seconds) is applied as the connect timeout and the read timeout of the HTTP retrieval, so a JWKS endpoint which never answers does not block every token for that signature configuration. A retrieval which times out counts as a failure and starts the back-off. Set it to `0s` to disable the timeout.

NOTE: The signature configuration for the `jwks_uri` of an OpenID client is registered as soon as the client is configured, even if the provider's discovery document could not be fetched when the application started. While the provider metadata is unavailable, tokens signed with the provider's keys are rejected, and unsigned tokens are rejected as always when a signature configuration exists. The metadata is fetched again on demand, at most once per `micronaut.security.token.jwt.signatures.jwks-client.failure-backoff` (default 10 seconds) and never on the thread verifying a token, so signed tokens are accepted once the provider becomes reachable, without restarting the application.

### Binding a JWKS to an issuer

When an application trusts the key sets of several identity providers, a key trusted for one provider must not be able to sign tokens that claim to be issued by another provider. A JWKS can be bound to an issuer with the `issuer` property. A bound JWKS only verifies tokens whose `iss` claim is equal to that issuer, tolerating only the case of the scheme and a trailing slash, the same comparison api:security.oauth2.endpoint.token.response.validation.IssuerClaimValidator[] applies to ID tokens. A different scheme, suffixes, parent domains and an empty `iss` never match; tokens issued by anyone else, or without an `iss` claim, are not verified with its keys, even if their signature validates against one of them.

[configuration]
----
micronaut:
  security:
    token:
      jwt:
        signatures:
          jwks:
            awscognito:
              url: 'https://cognito-idp.eu-west-1.amazonaws.com/eu-west-XXXXX/.well-known/jwks.json'
              issuer: 'https://cognito-idp.eu-west-1.amazonaws.com/eu-west-XXXXX'
----

The JWKS created for the `jwks_uri` of an <<openid-authorization-code, Open ID Connect>> client is always bound to the issuer of that client (the `issuer` asserted by the provider metadata or, if it asserts none, `micronaut.security.oauth2.clients.*.openid.issuer`). If neither `openid.issuer` is configured nor the provider metadata asserts an issuer (for example `fetch-configuration: false` with `openid.jwks-uri`), the JWKS is not bound and the application logs a warning once the provider metadata is resolved. Always set `openid.issuer` when several providers are trusted. A JWKS configured explicitly without an `issuer` verifies tokens regardless of their `iss` claim.

### Restricting the key type

By default, every key of the JWKS is used to verify token signatures, whatever its type (`kty`). If the identity provider publishes keys of several types but tokens must only be accepted when signed with one of them, restrict the JWKS with the `key-type` property. Only keys of the configured type are then used to verify a token; a token signed with a key of another type is rejected, even if that key is part of the JWKS. The value is case-insensitive and must be `RSA`, `EC`, `OKP` or `oct`; any other value fails application startup.

[configuration]
----
micronaut:
  security:
    token:
      jwt:
        signatures:
          jwks:
            awscognito:
              url: 'https://cognito-idp.eu-west-1.amazonaws.com/eu-west-XXXXX/.well-known/jwks.json'
              key-type: RSA
----
