Json Web Key Set (JWKS) fetched from a remote web server are cached. By default, they are cached via the internal bean api:security.token.jwt.signature.jwks.ReactorCacheJwkSetFetcher[] using
Project Reactor's `Mono::cacheInvalidateIf`. You can configure the cache expiration with `micronaut.security.token.jwt.signatures.jwks.*.cache-expiration`. It defaults to 60 seconds.

NOTE: However, we recommend you enable caching via https://micronaut-projects.github.io/micronaut-cache/latest/guide/[Micronaut Cache]. This will be the only option in the future.

**Caching via Micronaut Cache**

To cache JWKS with Micronaut Cache, you need to add an implementation of Micronaut Cache (E.g.
https://micronaut-projects.github.io/micronaut-cache/latest/guide/#caffeine[Caffeine],
https://micronaut-projects.github.io/micronaut-cache/latest/guide/#redis[Redis],
https://micronaut-projects.github.io/micronaut-cache/latest/guide/#ehcache[Ehcache],
https://micronaut-projects.github.io/micronaut-cache/latest/guide/#hazelcast[Hazelcast],
https://micronaut-projects.github.io/micronaut-coherence/latest/guide/#cache[Coherence],
https://micronaut-projects.github.io/micronaut-cache/latest/guide/#infinispan[Infinispan],
https://micronaut-projects.github.io/micronaut-eclipsestore/latest/guide/#cache[EclipseStore],
or https://micronaut-projects.github.io/micronaut-cache/latest/guide/#microstream[MicroStream]) and configure the expiration.

For example, you could add https://micronaut-projects.github.io/micronaut-cache/latest/guide/#caffeine[Caffeine] implementation:

dependency:micronaut-cache-caffeine[groupId=io.micronaut.cache]

The cache name is `jwks`. You can configure the cache expiration with:

[configuration]
----
micronaut:
  caches:
    jwks:
      expire-after-write: 24h
----

**Refresh on unknown key ID**

Authorization servers rotate their signing keys. When a JWT carries a `kid` header which is not present in the cached JWKS, Micronaut Security does not wait for the cache to expire: it clears the cached JWKS for that URL, fetches the JWKS again and verifies the token against the fresh keys. Tokens without a `kid` header, or whose `kid` is already present in the cached JWKS, never trigger a refresh.

To protect the authorization server from tokens with bogus key IDs, the refresh is rate limited per JWKS URL: at most one refresh happens per `micronaut.security.token.jwt.signatures.jwks.*.refresh-interval` (default 30 seconds). Requests with an unknown `kid` arriving within that interval are rejected without fetching the JWKS again.

[configuration]
----
micronaut:
  security:
    token:
      jwt:
        signatures:
          jwks:
            awscognito:
              url: 'https://cognito-idp.us-east-1.amazonaws.com/us-east-1_XXXX/.well-known/jwks.json'
              refresh-interval: 1m
----

**Failure back-off**

If a remote JWK Set cannot be retrieved (for example, the connection is refused, the endpoint responds with a non-2xx status or the body cannot be parsed) or the retrieved JWK Set contains no keys, the JWK Set is not requested again until a back-off elapses. While the back-off lasts, tokens which cannot be verified by another signature configuration are rejected without contacting the JWKS endpoint. This prevents an unauthenticated client from triggering one outbound JWKS request (and one error log entry) per request while the authorization server is unavailable.

The back-off applies to every api:security.token.jwt.signature.jwks.JwkSetFetcher[] implementation, including the Micronaut Cache based one. It is keyed by signature configuration name and JWKS url, since each configuration may use its own HTTP client settings, so a failure for one configuration does not prevent another configuration sharing the url from retrieving the JWK Set. You can configure its duration with:

[configuration]
----
micronaut:
  security:
    token:
      jwt:
        signatures:
          jwks-client:
            failure-backoff: 10s
            retrieval-timeout: 30s
----

`failure-backoff` defaults to 10 seconds. Set it to `0s` to disable the back-off and retry the retrieval for every token.

Concurrent requests share one retrieval per signature configuration and url. `retrieval-timeout` (default 30 seconds) bounds that shared retrieval even when the api:security.token.jwt.signature.jwks.JwksClient[] has no timeout of its own, so a retrieval which never completes does not block every token for that configuration. A retrieval which times out counts as a failure and starts the back-off. Set it to `0s` to disable the timeout.
