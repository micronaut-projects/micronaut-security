
This section will document breaking changes that may happen during milestone or release candidate releases, as well as major releases eg (1.x.x -> 2.x.x).

== Micronaut Security 4.18 breaking changes

- Starting with 4.18.2, when `micronaut.security.authentication` is set to `idtoken`, api:security.oauth2.client.IdTokenClaimsValidator[] ignores OAuth 2.0 clients configured with `micronaut.security.oauth2.clients.*.enabled: false`. ID tokens issued to a disabled client no longer authenticate requests as bearer tokens or JWT cookies. The OpenID provider metadata and the JWKS signature configuration of a disabled client are no longer registered. This removes only the trust that client itself contributed: if the claims validator is disabled with `micronaut.security.token.jwt.claims-validators.openid-idtoken: false`, a token issued to the disabled client is still accepted when an enabled client trusts the same issuer and signing keys, because nothing checks the `aud` claim. Keep api:security.oauth2.client.IdTokenClaimsValidator[], or an equivalent custom api:security.token.jwt.validator.GenericJwtClaimsValidator[], active to isolate clients that share an OpenID provider. In `idtoken` authentication mode, unsigned JWTs are now always rejected, including when every OAuth 2.0 client is disabled or none is configured and no JWKS signature configuration exists. api:security.oauth2.DefaultProviderResolver[] and the well-known proxy also ignore disabled clients. The constructor `DefaultProviderResolver(List<OpenIdClientConfiguration>)` has been deprecated. Use `DefaultProviderResolver(List<OpenIdClientConfiguration>, Collection<OauthClientConfiguration>)` instead.

- api:security.ldap.context.AttributesConvertibleValues[] no longer splits a single-valued LDAP attribute at commas when it is read as a collection or an array. Every attribute value is one element. As a result, api:security.ldap.group.DefaultLdapGroupProcessor[] maps an LDAP group named `Sales,Marketing` to the single role `Sales,Marketing` instead of the two roles `Sales` and `Marketing`. Applications relying on the previous splitting must map such groups themselves with a custom api:security.ldap.group.LdapGroupProcessor[].

- The `toString()` of all security events no longer includes the event source. api:security.token.event.AccessTokenGeneratedEvent[], api:security.token.event.RefreshTokenGeneratedEvent[] and api:security.event.TokenValidatedEvent[] no longer print the token, and the events extending api:security.event.SecurityEvent[] (api:security.event.LoginSuccessfulEvent[], api:security.event.LoginFailedEvent[], api:security.event.LogoutEvent[] and api:security.event.TokenValidatedEvent[]) no longer print the authentication or response they carry, whose attributes may hold tokens in OAuth 2.0 and OpenID Connect flows. Micronaut Framework logs every published event at `DEBUG` level with its string representation, which wrote these values to the log. Use `getSource()` or `getRefreshToken()` to obtain the value in your listeners.

- api:security.token.jwt.generator.SignedRefreshTokenGenerator[] no longer includes the token being validated in its `WARN` log messages. The introspection endpoint and the refresh token grant hand client-supplied tokens, such as other users' access tokens, to the refresh token validator, so the value was being written to the application log. The parse or verification exception is now logged at `DEBUG` without the token.

- Log statements no longer include credentials, tokens or claim values: the `Authorization` header (api:security.token.reader.HttpHeaderTokenReader[]), undecodable basic auth credentials (api:security.authentication.BasicAuthUtils[]), JSON Web Tokens verified or rejected by the signature validators and JWKS signatures, the claim set generated by api:security.token.jwt.generator.claims.JWTClaimsSetGenerator[] (only claim names are logged), the access tokens handled by the client credentials client, and the nonce and claims of an ID token that fails nonce validation. Applications relying on these log messages for troubleshooting no longer see the values.

- api:security.token.TokenAuthenticationFetcher[] consults the api:security.token.validator.TokenValidator[] beans one at a time, in order, and stops at the first validator which authenticates the token. Previously every validator was invoked concurrently for each token, which handed tokens already accepted by the JWT validator to lower precedence validators such as the OpenID provider `UserInfo` endpoint validator. Lower precedence validators are now only invoked once every preceding validator rejected the token. When the request carries several tokens, for example in a header and a cookie, they are likewise validated one at a time in the order the token readers resolve them.

- api:security.rules.IpPatternsRule[] no longer compiles every entry of `micronaut.security.ip-patterns` as a regular expression. An entry made only of hexadecimal digits, dots, colons and `*` (for example `127.0.0.1` or `192.168.1.*`) is now an IP wildcard whose dots and colons match literally. Previously `192.168.1.*` was the regular expression `192.168.1.*`, which also admitted `192.168.10.5` or `192.168.100.5`. Entries containing any other character (for example `192\.168\.1\.\d+`), and entries starting with a dot (for example the "allow all" regular expression `.*`), keep being compiled as regular expressions. A `*` in the middle of a wildcard matches within a single address segment (`192.168.*.1` does not match `192.168.2.3.1`), while a trailing `*` matches the rest of the address. To allow every address use `0.0.0.0`, `*` or `.*`.

- api:security.csrf.validator.CsrfTokenValidator[] no longer falls through to another api:security.csrf.repository.CsrfTokenRepository[] when the token found in a repository does not match the token supplied in the request. Repositories are consulted following their `Ordered` order and the first repository holding a CSRF token for the request is authoritative. api:security.csrf.session.SessionCsrfTokenRepository[] now runs before api:security.csrf.repository.CookieCsrfTokenRepository[]: with <<session, Session-Based Authentication>>, a request carrying an HTTP session which holds a CSRF token is only accepted when the supplied token matches the session token; a CSRF cookie does not replace it.

- api:security.oauth2.endpoint.token.response.DefaultOpenIdAuthenticationMapper[] qualifies the username with the provider name when more than one enabled OAuth 2.0 client, other than client-credentials-only clients, is configured under `micronaut.security.oauth2.clients`: `Authentication.getName()` is `<provider name>:<sub>` instead of `<sub>`, so that the same subject at two providers never maps to one user. With a single client the username remains the `sub` claim. The unqualified subject is kept in the `sub` attribute. The username of authentications created from an ID token with `micronaut.security.authentication` set to `idtoken` is not qualified. Applications with several clients which key data on the username must migrate those keys, or set `micronaut.security.oauth2.openid.qualify-username-with-provider` to `false` to restore the previous (unsafe) behavior. See <<openid-user-details, User Details Mapping>>.

- api:security.token.jwt.generator.claims.JWTClaimsSetGenerator[] now writes the `sub` claim after the authentication attributes, so the `sub` claim of a generated JWT is always `Authentication.getName()`. Previously an authentication attribute named `sub` replaced the principal name in the token, which turned a provider-qualified username back into the bare subject on every later request.

- The constructor `DefaultOpenIdAuthenticationMapper(OpenIdAdditionalClaimsConfiguration, AuthenticationModeConfiguration)` has been deprecated. Use `DefaultOpenIdAuthenticationMapper(OpenIdAdditionalClaimsConfiguration, AuthenticationModeConfiguration, OpenIdConfiguration, Collection<OauthClientConfiguration>)` instead.

- Starting with 4.18.2, `micronaut.security.token.jwt.signatures.jwks.*.key-type` is applied again when verifying token signatures with a remote JSON Web Key Set. Since 3.11.0 the setting had no effect: a token signed with a key of any type in the JWKS was accepted. A JWKS configured with a `key-type` now only verifies tokens signed with a key of that type. The setting no longer defaults to `RSA`; unless it is configured, keys of any type are matched, which preserves the previous behavior for applications that do not set it. `JwksSignatureConfigurationProperties.DEFAULT_KEYTYPE` is deprecated, and `JwksSignatureConfiguration.getKeyType()` returns `null` for a JWKS without a configured `key-type`. The `key-type` value is case-insensitive and must be one of `RSA`, `EC`, `OKP` or `oct`; any other value now fails application startup with a `ConfigurationException`. A key published in the JWKS with an explicit `alg` is only used to verify tokens whose header declares that algorithm; keys without `alg` match any algorithm.

- api:security.oauth2.endpoint.endsession.request.AbstractEndSessionRequest[] no longer expands the OpenID provider end session URL as a URI template. The logout parameters are percent-encoded and appended to the query component of the provider URL, preserving any query component it already has. If the provider URL is empty or not a valid URI, `getUrl(HttpRequest, Authentication)` returns `null` and `/oauth/logout` does not redirect, instead of throwing or redirecting to a malformed URL. The provider URL must be an absolute `http` or `https` URL with a host and without user information: a relative URL, another scheme, an empty or non-ASCII host, or `https://user:password@provider.example/logout` now results in this 404 response instead of being passed through. So does a provider URL that is not a strict RFC 3986 URI, for example one with an unencoded space or `{` in its path. Characters such as `{` or non-ASCII in the query component of the provider URL are percent-encoded, and a `;` in it is treated as a parameter separator.

- A failed retrieval of a remote JSON Web Key Set (connection error, non-2xx response, unparseable body or a JWK Set without keys) is no longer retried for every token. The JWK Set is not requested again until the back-off configured with `micronaut.security.token.jwt.signatures.jwks-client.failure-backoff` (default 10 seconds) elapses; tokens which cannot be verified by another signature configuration are rejected meanwhile. Set the property to `0s` to restore the previous behavior. Concurrent requests share one retrieval per signature configuration and url, bounded by `micronaut.security.token.jwt.signatures.jwks-client.retrieval-timeout` (default 30 seconds); a retrieval which exceeds it is treated as a failure.

- api:security.token.jwt.signature.jwks.JwkSetFetcher[] `clearCache(url)` now also evicts the JWK Set cached by the caching implementations (the Reactor based one evicts the entries for that url; the Micronaut Cache based one evicts the whole `jwks` cache, since its entries are keyed by provider name and url) in addition to the AOT optimization and the failure back-off.

- The constructor `DefaultJwkSetFetcher(JwksClient)` has been deprecated. Use `DefaultJwkSetFetcher(JwksClient, JwksClientConfiguration)` instead.

- api:security.errors.CookiePriorToLoginPersistence[] only stores the path and query of the request rejected prior to login, and only honours a local path (one starting with a single `/`) when redirecting after login. Scheme-relative (`//host/...`) or absolute URIs are ignored and the login handlers fall back to `micronaut.security.redirect.login-success`.

- The plain OAuth 2.0 client (api:security.oauth2.client.DefaultOauthClient[]) now sends the application's own callback URL, built with api:security.oauth2.url.OauthRouteUrlBuilder[], as the `redirect_uri` parameter of the authorization code grant token request. Previously the value stored in the `state` parameter of the authorization response was used, which allowed anyone redirecting the browser to the callback endpoint to choose the `redirect_uri` sent to the provider and redeem an authorization code issued for a different redirection URI (RFC 6749 sections 4.1.3 and 10.6). The OpenID Connect client already behaved this way.

- The constructor `DefaultOauthAuthorizationResponseHandler(TokenEndpointClient, StateValidator, PkcePersistence)` has been deprecated. Use `DefaultOauthAuthorizationResponseHandler(TokenEndpointClient, OauthRouteUrlBuilder, StateValidator, PkcePersistence)` instead.

- The constructor `OauthCodeTokenRequestContext(AuthorizationResponse, SecureEndpoint, OauthClientConfiguration, String)` has been deprecated. Use `OauthCodeTokenRequestContext(AuthorizationResponse, OauthRouteUrlBuilder, SecureEndpoint, OauthClientConfiguration, String)` instead. A context created with the deprecated constructor no longer sends a `redirect_uri` parameter to the token endpoint.

- Starting with 4.18.2, the JSON Web Key Set published at the `jwks_uri` of an OpenID provider is registered as a signature configuration for request tokens only when `micronaut.security.authentication` is set to `idtoken`, as it was before Micronaut Security 4.8.0. In `cookie`, `session` and `bearer` modes, or when the authentication mode is not set, tokens signed by the provider's keys, such as ID tokens issued to other clients, no longer authenticate requests. Applications that must accept the provider's tokens as request credentials in those modes need to configure the JWKS explicitly with `micronaut.security.token.jwt.signatures.jwks.*`.

- The ID token returned by the token endpoint during the authorization code flow is verified exclusively against the issuing provider's JWKS. It is no longer accepted when signed by any other signature configuration of the application.

- Single-valued keys directly under `micronaut.security.ldap`, such as the global switch `micronaut.security.ldap.enabled`, no longer create an api:security.ldap.configuration.LdapConfiguration[] named after the key. Previously `micronaut.security.ldap.enabled: true` created a configuration and an api:security.ldap.LdapAuthenticationProvider[] named `enabled` with no server, whose failures turned login attempts for unknown usernames into HTTP 500 responses and allowed username enumeration. Only keys with nested properties, for example `micronaut.security.ldap.default.*`, define LDAP configurations.

- api:security.ldap.LdapAuthenticationProvider[] no longer returns `AuthenticationFailureReason.USER_NOT_FOUND` when the username does not match any directory entry. It returns `CREDENTIALS_DO_NOT_MATCH`, the same reason as for a wrong password, and attempts a bind against a decoy DN (a random non-existent entry under the search base, or the entry configured with `micronaut.security.ldap.*.search.decoy-dn`) so that unknown usernames cannot be enumerated through the failure message and the response-time difference is narrowed. Only the client-side cost is equalised by default; see the <<ldap, LDAP>> section for configuring a decoy account where directory-side timing matters.

- The api:security.authentication.Authentication[] created by the `UserInfo` endpoint token validator is bound to the provider which answered. The attribute `oauth2Provider` is always set to the provider name, and when `micronaut.security.oauth2.openid.qualify-username-with-provider` is `true`, or it is not set and more than one enabled OAuth 2.0 client is configured under `micronaut.security.oauth2.clients`, the username is `<provider name>:<sub>` instead of `<sub>`, so that the same subject at two providers never maps to one user. Applications with several clients which key data on `Authentication.getName()` for `UserInfo`-validated requests must migrate those keys. Client names under `micronaut.security.oauth2.clients` containing `:` are not supported by the configuration binding, and the `UserInfo` validator additionally rejects them with a `ConfigurationException` when usernames are qualified, since they would make the qualified name ambiguous. See the <<user-info, UserInfo Endpoint>> section.

- With `micronaut.security.authentication` set to `idtoken`, api:security.oauth2.endpoint.endsession.request.OktaEndSessionEndpoint[] (used for Okta and Oracle Cloud) only sends as `id_token_hint` the token which authenticated the request, as recorded in the api:security.context.SecurityContext[]. Previously, it sent the first token found in the request, which could be an unrelated `Authorization: Bearer` header added by a gateway rather than the ID token cookie. If no token authenticated the request and the authentication has no `openIdToken` attribute, no `id_token_hint` is sent.

- Starting with 4.18.2, api:security.oauth2.endpoint.token.response.validation.IssuerClaimValidator[] requires the `iss` claim of an ID token to match the issuer expected for the OpenID client in addition to the Issuer Identifier of the provider metadata. The expected issuer is `micronaut.security.oauth2.clients.*.openid.issuer`, or `micronaut.security.oauth2.clients.*.openid.issuer-identifier` when set. The comparison is exact, tolerating only the case of the scheme and a trailing slash. Moreover, an `issuer` announced in the provider's discovery document that does not match the expected issuer is discarded (an error is logged) and the expected issuer is used instead, as required by OpenID Connect Discovery 1.0 section 4.3. ID tokens whose `iss` claim only matched the issuer announced by the provider are now rejected. If the provider issues tokens with an `iss` that differs from the URL used to fetch the discovery document (for example, discovery over a cluster-internal URL, or Oracle IDCS with a tenant specific `issuer` and the provider wide issuer `https://identity.oraclecloud.com/`), set `micronaut.security.oauth2.clients.*.openid.issuer-identifier` to the expected `iss` value.

== Micronaut Security 4.0 breaking changes

- api:security.rules.SecurityRule[] `check` method no longer contains the argument `RouteMatch`. You can easily retrieve a `RouteMatch`
with the `HttpRequest` method argument with `request.getAttribute(HttpAttributes.ROUTE_MATCH).orElse(null)`.

- For applications with `micronaut.security.authentication` set to `cookie` and `micronaut.security.redirect.enabled` set to `false`, the server responds with 401 HTTP Status code instead of 200 for login failed attempts.

- `micronaut.security.intercept-url-map-prepend-pattern-with-context-path` defaults to `true`. Thus intercept url patterns are be prepended with the server context path if it is set.

- Micronaut Security APIs have been decoupled from HTTP. Many APIs now have generics instead of HTTP-related types such as `HttpRequest`.
For example,  instead of `AuthenticationProvider`, you should use `AuthenticationProvider<HttpRequest<?>>`.

=== SecurityRule Changes

The api:security.rules.SecurityRule[] API has changed. The last argument to the method was a map that represented the user attributes. Instead that argument was replaced with a reference to the api:security.authentication.Authentication[]. This has the benefit of rules now having access to the username of the logged in user as well as access to the convenience method `getRoles()`.

In addition, the return type of the method has changed to return a `Publisher`. This was necessary because the security rules execute as part of the security filter which may be on a non blocking thread. Because the method now returns a `Publisher`, blocking operations can be offloaded to another thread pool using the reactive streams implementation of your choice.

Micronaut 2 API:

`SecurityRuleResult check(HttpRequest<?> request, @Nullable RouteMatch<?> routeMatch, @Nullable Map<String, Object> claims);`

Micronaut 3 API:

`Publisher<SecurityRuleResult> check(HttpRequest<?> request, @Nullable RouteMatch<?> routeMatch, @Nullable Authentication authentication);`

All classes in the `io.micronaut.configuration.security.ldap` have been moved to the `io.micronaut.security.ldap` package.
