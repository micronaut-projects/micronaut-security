
This section will document breaking changes that may happen during milestone or release candidate releases, as well as major releases eg (1.x.x -> 2.x.x).

== Micronaut Security 3.11 breaking changes

- api:security.authentication.Authenticator[] evaluates the authentication providers one at a time in precedence order instead of subscribing to all of them concurrently. With the default `micronaut.security.authentication-provider-strategy: ANY`, the response of the highest precedence provider that accepts the credentials is used, regardless of how fast the other providers answer, and lower precedence providers are not subscribed to once a provider has accepted the credentials. Previously the response of the fastest provider was used, so a user accepted by several providers could be granted the roles of a lower precedence provider. With the `ALL` strategy the providers are still all evaluated, sequentially, and the response of the first provider in precedence order that accepts the credentials is used.

- Starting with 3.11.3, issuer claim matching for the OpenID client validators is stricter. Previously api:security.oauth2.DefaultProviderResolver[] resolved a client when the configured issuer merely started with the `iss` claim (so an empty `iss`, or `h`, matched every client) and api:security.oauth2.client.IdTokenClaimsValidator[] compared the `iss` claim case-insensitively. Now the `iss` claim must be identical to the expected issuer (`micronaut.security.oauth2.clients.*.openid.issuer-identifier` if set, otherwise `openid.issuer`), as OpenID Connect Core 1.0 section 3.1.3.7 requires: only the case of the scheme and a single trailing slash (when the issuer has no query or fragment) are tolerated, so an `http://` claim does not match an `https://` issuer and the host is compared case-sensitively. This is the same comparison api:security.oauth2.endpoint.token.response.validation.IssuerClaimValidator[] and the issuer binding of the JWKS use. If your provider issues tokens whose `iss` differs from the configured issuer, configure the exact `iss` value with `openid.issuer-identifier` (for example `https://identity.oraclecloud.com/` for Oracle IDCS, whose tenant specific `openid.issuer` is only the discovery URL).
api:security.token.jwt.validator.IssuerJwtClaimsValidator[] keeps comparing the `iss` claim verbatim with `micronaut.security.token.jwt.claims-validators.issuer`. If that property is present but has no value (for example `issuer:` in YAML), the validator now rejects every token and logs a warning at startup; previously it accepted any `iss` claim.

- Starting with 3.11.3, when `micronaut.security.authentication` is set to `idtoken`, api:security.oauth2.client.IdTokenClaimsValidator[] ignores OAuth 2.0 clients configured with `micronaut.security.oauth2.clients.*.enabled: false`. ID tokens issued to a disabled client no longer authenticate requests as bearer tokens or JWT cookies. The OpenID provider metadata and the JWKS signature configuration of a disabled client are no longer registered. This removes only the trust that client itself contributed: if the claims validator is disabled with `micronaut.security.token.jwt.claims-validators.openid-idtoken: false`, a token issued to the disabled client is still accepted when an enabled client trusts the same issuer and signing keys, because nothing checks the `aud` claim. Keep api:security.oauth2.client.IdTokenClaimsValidator[], or an equivalent custom api:security.token.jwt.validator.GenericJwtClaimsValidator[], active to isolate clients that share an OpenID provider. In `idtoken` authentication mode, unsigned JWTs are now always rejected, including when every OAuth 2.0 client is disabled or none is configured and no JWKS signature configuration exists. api:security.oauth2.DefaultProviderResolver[] also ignores disabled clients. The constructor `DefaultProviderResolver(List<OpenIdClientConfiguration>)` has been deprecated. Use `DefaultProviderResolver(List<OpenIdClientConfiguration>, Collection<OauthClientConfiguration>)` instead.

- api:security.ldap.context.AttributesConvertibleValues[] no longer splits a single-valued LDAP attribute at commas when it is read as a collection or an array. Every attribute value is one element. As a result, api:security.ldap.group.DefaultLdapGroupProcessor[] maps an LDAP group named `Sales,Marketing` to the single role `Sales,Marketing` instead of the two roles `Sales` and `Marketing`. Applications relying on the previous splitting must map such groups themselves with a custom api:security.ldap.group.LdapGroupProcessor[].

- The `toString()` of all security events no longer includes the event source. api:security.token.event.AccessTokenGeneratedEvent[], api:security.token.event.RefreshTokenGeneratedEvent[] and api:security.event.TokenValidatedEvent[] no longer print the token, and the other security events (api:security.event.LoginSuccessfulEvent[], api:security.event.LoginFailedEvent[], api:security.event.LogoutEvent[] and api:security.event.TokenValidatedEvent[]) no longer print the authentication or response they carry, whose attributes may hold tokens in OAuth 2.0 and OpenID Connect flows. Micronaut Framework logs every published event at `DEBUG` level with its string representation, which wrote these values to the log. Use `getSource()` or `getRefreshToken()` to obtain the value in your listeners.

- api:security.token.jwt.generator.SignedRefreshTokenGenerator[] no longer includes the token being validated in its `WARN` log messages. The introspection endpoint and the refresh token grant hand client-supplied tokens, such as other users' access tokens, to the refresh token validator, so the value was being written to the application log. The parse or verification exception is now logged at `DEBUG` without the token.

- Log statements no longer include credentials, tokens or claim values: the `Authorization` header (api:security.token.reader.HttpHeaderTokenReader[]), undecodable basic auth credentials (api:security.authentication.BasicAuthUtils[]), JSON Web Tokens rejected by api:security.token.jwt.validator.JwtValidator[], the claim set generated by api:security.token.jwt.generator.claims.JWTClaimsSetGenerator[] (only claim names are logged), the access tokens handled by the client credentials client, and the nonce and claims of an ID token that fails nonce validation. Applications relying on these log messages for troubleshooting no longer see the values.

- api:security.token.TokenAuthenticationFetcher[] consults the api:security.token.validator.TokenValidator[] beans one at a time, in order, and stops at the first validator which authenticates the token. Previously every validator was invoked concurrently for the token, which handed tokens already accepted by the JWT validator to lower precedence validators, including validators which send the token to a remote service. A custom validator is now only invoked once every validator preceding it has rejected the token.

- api:security.rules.IpPatternsRule[] no longer compiles every entry of `micronaut.security.ip-patterns` as a regular expression. An entry made only of hexadecimal digits, dots, colons and `*` (for example `127.0.0.1` or `192.168.1.*`) is now an IP wildcard whose dots and colons match literally. Previously `192.168.1.*` was the regular expression `192.168.1.*`, which also admitted `192.168.10.5` or `192.168.100.5`. Entries containing any other character (for example `192\.168\.1\.\d+`), and entries starting with a dot (for example the "allow all" regular expression `.*`), keep being compiled as regular expressions. A `*` in the middle of a wildcard matches within a single address segment (`192.168.*.1` does not match `192.168.2.3.1`), while a trailing `*` matches the rest of the address. To allow every address use `0.0.0.0`, `*` or `.*`.

- api:security.oauth2.endpoint.token.response.DefaultOpenIdAuthenticationMapper[] qualifies the username with the provider name when more than one enabled OAuth 2.0 client, other than client-credentials-only clients, is configured under `micronaut.security.oauth2.clients`: `Authentication.getName()` is `<provider name>:<sub>` instead of `<sub>`, so that the same subject at two providers never maps to one user. With a single client the username remains the `sub` claim. The unqualified subject is kept in the `sub` attribute. The username of authentications created from an ID token with `micronaut.security.authentication` set to `idtoken` is not qualified. Applications with several clients which key data on the username must migrate those keys, or set `micronaut.security.oauth2.openid.qualify-username-with-provider` to `false` to restore the previous (unsafe) behavior. See <<openid-user-details, User Details Mapping>>.

- api:security.token.jwt.generator.claims.JWTClaimsSetGenerator[] now writes the `sub` claim after the authentication attributes, so the `sub` claim of a generated JWT is always `Authentication.getName()`. Previously an authentication attribute named `sub` replaced the principal name in the token, which turned a provider-qualified username back into the bare subject on every later request.

- The constructor `DefaultOpenIdAuthenticationMapper(OpenIdAdditionalClaimsConfiguration, AuthenticationModeConfiguration)` has been deprecated. Use `DefaultOpenIdAuthenticationMapper(OpenIdAdditionalClaimsConfiguration, AuthenticationModeConfiguration, OpenIdConfiguration, Collection<OauthClientConfiguration>)` instead.

- Starting with 3.11.3, `micronaut.security.token.jwt.signatures.jwks.*.key-type` is applied again when verifying token signatures with a remote JSON Web Key Set. Since 3.11.0 the setting had no effect: a token signed with a key of any type in the JWKS was accepted. A JWKS configured with a `key-type` now only verifies tokens signed with a key of that type. The setting no longer defaults to `RSA`; unless it is configured, keys of any type are matched, which preserves the previous behavior for applications that do not set it. `JwksSignatureConfigurationProperties.DEFAULT_KEYTYPE` is deprecated, and `JwksSignatureConfiguration.getKeyType()` returns `null` for a JWKS without a configured `key-type`. The `key-type` value is case-insensitive and must be one of `RSA`, `EC`, `OKP` or `oct`; any other value now fails application startup with a `ConfigurationException`. A key published in the JWKS with an explicit `alg` is only used to verify tokens whose header declares that algorithm; keys without `alg` match any algorithm.

- api:security.oauth2.endpoint.endsession.request.AbstractEndSessionRequest[] no longer expands the OpenID provider end session URL as a URI template. The logout parameters are percent-encoded and appended to the query component of the provider URL, preserving any query component it already has. If the provider URL is empty or not a valid URI, `getUrl(HttpRequest, Authentication)` returns `null` and `/oauth/logout` does not redirect, instead of throwing or redirecting to a malformed URL. The provider URL must be an absolute `http` or `https` URL with a host and without user information: a relative URL, another scheme, an empty or non-ASCII host, or `https://user:password@provider.example/logout` now results in this 404 response instead of being passed through. So does a provider URL that is not a strict RFC 3986 URI, for example one with an unencoded space or `{` in its path. Characters such as `{` or non-ASCII in the query component of the provider URL are percent-encoded, and a `;` in it is treated as a parameter separator.

- A failed retrieval of a remote JSON Web Key Set (connection error, non-2xx response, unparseable body or a JWK Set without keys) is no longer retried for every token. The JWK Set is not requested again until the back-off configured with `micronaut.security.token.jwt.signatures.jwks-client.failure-backoff` (default 10 seconds) elapses; tokens which cannot be verified by another signature configuration are rejected without contacting the JWKS endpoint. Set the property to `0s` to restore the previous behavior. The retrieval is bounded by `micronaut.security.token.jwt.signatures.jwks-client.retrieval-timeout` (default 30 seconds), applied as the connect and read timeout.

- The constructor `DefaultJwkSetFetcher()` has been deprecated. Use `DefaultJwkSetFetcher(JwksClientConfiguration)` instead.

- api:security.errors.CookiePriorToLoginPersistence[] only stores the path and query of the request rejected prior to login, and only honours a local path (one starting with a single `/`) when redirecting after login. Scheme-relative (`//host/...`) or absolute URIs are ignored and the login handlers fall back to `micronaut.security.redirect.login-success`.

- The plain OAuth 2.0 client (api:security.oauth2.client.DefaultOauthClient[]) now sends the application's own callback URL, built with api:security.oauth2.url.OauthRouteUrlBuilder[], as the `redirect_uri` parameter of the authorization code grant token request. Previously the value stored in the `state` parameter of the authorization response was used, which allowed anyone redirecting the browser to the callback endpoint to choose the `redirect_uri` sent to the provider and redeem an authorization code issued for a different redirection URI (RFC 6749 sections 4.1.3 and 10.6). The OpenID Connect client already behaved this way.

- The constructor `DefaultOauthAuthorizationResponseHandler(TokenEndpointClient, StateValidator, PkcePersistence)` has been deprecated. Use `DefaultOauthAuthorizationResponseHandler(TokenEndpointClient, OauthRouteUrlBuilder, StateValidator, PkcePersistence)` instead.

- The constructor `OauthCodeTokenRequestContext(AuthorizationResponse, SecureEndpoint, OauthClientConfiguration, String)` has been deprecated. Use `OauthCodeTokenRequestContext(AuthorizationResponse, OauthRouteUrlBuilder, SecureEndpoint, OauthClientConfiguration, String)` instead. A context created with the deprecated constructor no longer sends a `redirect_uri` parameter to the token endpoint.

- Starting with 3.11.3, in `idtoken` authentication mode the JWKS signature configuration of an enabled OpenID client is registered as soon as the client is configured, even if the provider's discovery document cannot be fetched when the application starts. Previously a provider unreachable at startup left the application without that signature configuration until it was restarted, so tokens signed by the provider were rejected until then, and, before unsigned tokens were rejected in `idtoken` mode regardless of the registered signature configurations, an application relying on an OpenID client as its only source of verification keys accepted unsigned (`alg=none`) tokens. The `jwks_uri` and the issuer are now resolved from the provider metadata on demand, bounded by `micronaut.security.token.jwt.signatures.jwks-client.failure-backoff`; tokens signed with the provider's keys are rejected while the metadata is unavailable. The api:security.token.jwt.signature.jwks.JwksSignature[] bean of an OpenID client is now created from a `JwksSignatureConfiguration` bean named after the client, whose `getUrl()` throws an `IllegalStateException` while the provider metadata is unavailable; api:security.token.jwt.signature.jwks.JwksSignature[] treats that as a failed verification. The internal factory method `JwksUriSignatureFactory#createJwksUriSignature(OpenIdClientConfiguration, BeanProvider, JwkValidator, JwkSetFetcher)` has been replaced by `createJwksSignatureConfiguration(OpenIdClientConfiguration, ExecutorService, JwksClientConfiguration)`.

- Single-valued keys directly under `micronaut.security.ldap`, such as the global switch `micronaut.security.ldap.enabled`, no longer create an api:security.ldap.configuration.LdapConfiguration[] named after the key. Previously `micronaut.security.ldap.enabled: true` created a configuration and an api:security.ldap.LdapAuthenticationProvider[] named `enabled` with no server, whose failures turned login attempts for unknown usernames into HTTP 500 responses and allowed username enumeration. Only keys with nested properties, for example `micronaut.security.ldap.default.*`, define LDAP configurations.

- The HTTP clients Micronaut Security creates to talk to an identity provider (token endpoint and OpenID provider metadata discovery) no longer follow redirects, regardless of `micronaut.http.client.follow-redirects`, and the JDK connection used to retrieve a remote JWK Set no longer follows redirects either. A redirect returned by the provider is never followed, so the request fails instead of reaching the redirect target. An `HttpClient` bean named after an OAuth 2.0 provider is no longer used to call its token endpoint: a client that never follows redirects is created from the service configuration `micronaut.http.services.<provider>.*`, or from the default client configuration, instead. See <<providerHttpClient, HTTP Clients for the Provider>>.

- The constructor `OpenIdProviderMetadataFetcherFactory()` has been replaced by `OpenIdProviderMetadataFetcherFactory(BeanContext, HttpClientConfiguration)` and the factory method `createOpenIdProviderMetadataFetcher(OpenIdClientConfiguration, HttpClient)` by `createOpenIdProviderMetadataFetcher(OpenIdClientConfiguration)`. The class is internal API.

- Starting with 3.11.3, the JSON Web Key Set registered for the `jwks_uri` of an OpenID client is bound to the issuer of that client (the `issuer` asserted by the provider metadata or, if it asserts none, `micronaut.security.oauth2.clients.*.openid.issuer`). Tokens whose `iss` claim is not equal to the issuer (tolerating only the case of the scheme and a trailing slash), or that have no or an empty `iss` claim, are no longer verified with the keys of that provider, even if their signature validates against one of them. This prevents a key trusted for one provider from signing tokens as another provider. Applications that must verify tokens of a different issuer with a provider's keys need to configure the JWKS explicitly with `micronaut.security.token.jwt.signatures.jwks.*.url`, optionally bound to the expected issuer with `micronaut.security.token.jwt.signatures.jwks.*.issuer`.

- api:security.ldap.LdapAuthenticationProvider[] no longer returns `AuthenticationFailureReason.USER_NOT_FOUND` when the username does not match any directory entry. It returns `CREDENTIALS_DO_NOT_MATCH`, the same reason as for a wrong password, and attempts a bind against a decoy DN (a random non-existent entry under the search base, or the entry configured with `micronaut.security.ldap.*.search.decoy-dn`) so that unknown usernames cannot be enumerated through the failure message and the response-time difference is narrowed. Only the client-side cost is equalised by default; see the <<ldap, LDAP>> section for configuring a decoy account where directory-side timing matters.

- With `micronaut.security.authentication` set to `idtoken`, api:security.oauth2.endpoint.endsession.request.OktaEndSessionEndpoint[] (used for Okta and Oracle Cloud) only sends as `id_token_hint` the token which authenticated the request, as recorded in the request attribute `micronaut.TOKEN` by the token authentication fetcher. Previously, it sent the first token found in the request, which could be an unrelated `Authorization: Bearer` header added by a gateway rather than the ID token cookie. If no token authenticated the request and the authentication has no `openIdToken` attribute, no `id_token_hint` is sent.

- api:security.oauth2.DefaultProviderResolver[] no longer picks the first OpenID client whose issuer matches the `iss` claim when the claim matches several enabled clients. The `aud` claim (and the `azp` claim for multi-audience tokens) must identify exactly one of them by `client-id`; otherwise no provider is resolved and `/oauth/logout` does not redirect to any provider. Previously the user, and with Oracle Cloud or Okta their ID token, could be sent to the wrong provider's end session endpoint, for example when two Oracle Cloud identity domains, whose ID tokens share the issuer `https://identity.oraclecloud.com/`, are configured. Moreover, with `micronaut.security.authentication` set to `idtoken`, api:security.oauth2.client.IdTokenClaimsValidator[] rejects ID tokens carrying a claim named `oauth2Provider` or `openIdToken`. Those names are reserved for the authentication attributes the application sets during the authorization code flow, which `/oauth/logout` trusts to pick the provider; since the attributes of an authentication created from an ID token are the claims of the token, a provider emitting such a claim could otherwise have the token sent to another client's end session endpoint. The validator also compares the `azp` claim with the client id case-sensitively; previously the comparison ignored case. See <<endsession, End Session>>.

- Starting with 3.11.3, api:security.oauth2.endpoint.token.response.validation.IssuerClaimValidator[] requires the `iss` claim of an ID token to match the issuer expected for the OpenID client in addition to the Issuer Identifier of the provider metadata. The expected issuer is `micronaut.security.oauth2.clients.*.openid.issuer`, or `micronaut.security.oauth2.clients.*.openid.issuer-identifier` when set. The comparison is exact, tolerating only the case of the scheme and a trailing slash. Moreover, an `issuer` announced in the provider's discovery document that does not match the expected issuer is discarded (an error is logged) and the expected issuer is used instead, as required by OpenID Connect Discovery 1.0 section 4.3. ID tokens whose `iss` claim only matched the issuer announced by the provider are now rejected. If the provider issues tokens with an `iss` that differs from the URL used to fetch the discovery document (for example, discovery over a cluster-internal URL, or Oracle IDCS with a tenant specific `issuer` and the provider wide issuer `https://identity.oraclecloud.com/`), set `micronaut.security.oauth2.clients.*.openid.issuer-identifier` to the expected `iss` value.

==== Other Changes

- The api:security.event.LoginSuccessfulEvent[] that gets emitted when a user logs in will now be created with an instance of api:security.authentication.Authentication[].
- The `AuthenticationUserDetailsAdapter` class has been deleted.

=== SecurityRule Changes

The api:security.rules.SecurityRule[] API has changed. The last argument to the method was a map that represented the user attributes. Instead that argument was replaced with a reference to the api:security.authentication.Authentication[]. This has the benefit of rules now having access to the username of the logged in user as well as access to the convenience method `getRoles()`.

In addition, the return type of the method has changed to return a `Publisher`. This was necessary because the security rules execute as part of the security filter which may be on a non blocking thread. Because the method now returns a `Publisher`, blocking operations can be offloaded to another thread pool using the reactive streams implementation of your choice.

Micronaut 2 API:

`SecurityRuleResult check(HttpRequest<?> request, @Nullable RouteMatch<?> routeMatch, @Nullable Map<String, Object> claims);`

Micronaut 3 API:

`Publisher<SecurityRuleResult> check(HttpRequest<?> request, @Nullable RouteMatch<?> routeMatch, @Nullable Authentication authentication);`

=== LDAP Package Change

All classes in the `io.micronaut.configuration.security.ldap` have been moved to the `io.micronaut.security.ldap` package.

=== SecurityFilter

The security filter no longer extends deprecated `OncePerRequestHttpServerFilter` because it has been deprecated in Micronaut 3.

=== Cookie Secure Configuration

The following properties' default value has been removed in Micronaut Security 3.0.0:

- `micronaut.security.oauth2.openid.nonce.cookie.cookie-secure`
- `micronaut.security.oauth2.state.cookie.cookie-secure`
- `micronaut.security.token.jwt.cookie.cookie-secure`
- `micronaut.security.token.refresh.cookie.cookie-secure``

NOTE: If the `cookie-secure` setting is not set, cookies will be secure if the request is determined to be HTTPS.

=== Deprecations Removal

Most if not all deprecated classes constructors, and methods have been removed.

=== Other Changes

- The constructor of api:security.token.jwt.validator.DefaultJwtAuthenticationFactory[] has changed
- The constructor of api:security.oauth2.endpoint.token.response.IdTokenLoginHandler[] has changed
- The constructor of api:security.session.SessionLoginHandler[] has changed
- The constructor of api:security.authentication.BasicAuthAuthenticationFetcher[] has changed
- The api:io.micronaut.security.token.RolesFinder[] method `findInClaims` has been deprecated and usages should be replaced with `resolveRoles(@Nullable Map<String, Object> attributes)`.
