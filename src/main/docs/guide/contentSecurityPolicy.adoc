https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP[Content Security Policy (CSP)] is a browser-enforced, defense-in-depth mechanism that restricts which resources a page may load and what actions it may perform. A carefully designed policy can reduce the impact of content injection vulnerabilities such as cross-site scripting (XSS), but it does not replace output encoding, input validation, or other secure coding practices.

The `micronaut-security-csp` module generates a policy for each request and writes it to the HTTP response. When nonce support is enabled, it also stores the request nonce as a request attribute. The module does not add the nonce to view models itself; Micronaut Views 6.3.1 does not do it either, so register a view model processor as shown in <<cspNonceGeneration,script-src Nonces>> to use the nonce in templates.

NOTE: Adding the module enables its restrictive default policy. Existing applications will normally need to allow the resources they intentionally use before deploying the policy in enforcing mode. Use <<cspReportOnly,report-only mode>> while evaluating violations.

NOTE: If you are migrating from the CSP support in Micronaut Views, disable it with `micronaut.views.csp.enabled: false` and see <<cspMigratingFromViews,Migrating from Micronaut Views>>. Both store their nonce in the `cspNonce` request attribute, so the application fails to start while both are enabled.

WARNING: The module is part of Micronaut Security. When `micronaut-security` is on the classpath, `micronaut.security.enabled: false` disables this module too, so no CSP header is written and no nonce is generated. An application that disables Micronaut Security because a gateway authenticates requests, and still wants the policy, must keep `micronaut.security.enabled` unset or `true`.
