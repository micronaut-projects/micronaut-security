The https://tools.ietf.org/html/rfc7662#section-5.1[Introspection endpoint] exposes an endpoint to inquire the current state of a token.

[source, bash]
----
POST /token_info
Accept: application/json
Content-Type: application/x-www-form-urlencoded
Authorization: Basic dXNlcjpwYXNzd29yZA==
token=eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiYWRtaW4iOnRydWUsImp0aSI6IjM1NjhjM2EzLWFlMmMtNDFiMy1hYzU5LTU0ZTkxODVkM2ViOCIsImlhdCI6MTYwMTA0OTU5OCwiZXhwIjoxNjAxMDUzMTk4fQ.Sc5Xh7jI6e_F3FAUo3n3AUCHNSxWH8t-WlM6JxeHZGI&token_type_hint=access_token
----

Moreover, you can access a secured GET endpoint which responds the introspection response for the authenticated user:

[source, bash]
----
GET /token_info
Accept: application/json
Authorization: Bearer eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiYWRtaW4iOnRydWUsImp0aSI6IjM1NjhjM2EzLWFlMmMtNDFiMy1hYzU5LTU0ZTkxODVkM2ViOCIsImlhdCI6MTYwMTA0OTU5OCwiZXhwIjoxNjAxMDUzMTk4fQ.Sc5Xh7jI6e_F3FAUo3n3AUCHNSxWH8t-WlM6JxeHZGI
----

responds:

[source, json]
----
{
 "active": false
 "username": "1234567890",
 "sub": "1234567890",
 "name": "John Doe",
 "admin": true,
 "jti": "3568c3a3-ae2c-41b3-ac59-54e9185d3eb8",
 "iat": 1601049598,
 "exp": 1601053198
}
----

If no api:security.token.validator.TokenValidator[] accepts the token, the endpoint treats it as a refresh token. The token is first checked with the api:security.token.validator.RefreshTokenValidator[] and, when a api:security.token.refresh.RefreshTokenPersistence[] bean is present, it is then looked up in the persistence layer:

* If `RefreshTokenPersistence::getAuthentication` emits an api:security.authentication.Authentication[], the refresh token is reported as `"active": true` and the response is populated from that `Authentication` (for example `username`, `sub` and roles), the same way as for an access token. The response does not say that the token is a refresh token; resource servers must not accept a refresh token as an access token based on this response.
* If it emits nothing or fails (for example, because the refresh token was revoked or the persistence layer is unavailable), the refresh token is reported as `"active": false`. A failure other than an api:security.errors.OauthErrorResponseException[] is logged at `WARN` by api:security.endpoints.introspection.DefaultIntrospectionProcessor[], so check that logger when refresh tokens are unexpectedly reported inactive.

IMPORTANT: Because introspection calls `RefreshTokenPersistence::getAuthentication`, the method must not have side effects. Keep refresh token rotation, single-use bookkeeping or reuse detection out of it; otherwise introspecting a refresh token consumes or revokes it. For a revoked or unknown refresh token, emit no item or an `OauthErrorResponseException` with the `invalid_grant` error code. The returned publisher may be subscribed on a Netty event loop thread; if the lookup blocks (for example, JDBC or JPA), subscribe it on a scheduler for blocking work, for example `Mono.fromCallable(...).subscribeOn(Schedulers.fromExecutorService(blockingExecutor))`.

NOTE: Configure a refresh token secret (`micronaut.security.token.jwt.generator.refresh-token.secret`) different from the access token signing secret. Otherwise the api:security.token.validator.RefreshTokenValidator[] also accepts an expired access token, which is then looked up in `RefreshTokenPersistence` in vain.

If there is no `RefreshTokenPersistence` bean, there is no revocation point to consult; a refresh token is reported as `"active": true`, with no other fields, as soon as the `RefreshTokenValidator` accepts it and for as long as it remains valid. Refresh tokens revoked elsewhere are still reported active.
