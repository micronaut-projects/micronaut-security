IMPORTANT: https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html#signed-double-submit-cookie-recommended[Signed Double-Submit Cookie]. Sign the CSRF Token with to prevent attackers from overriding the cookie value with their own (e.g. with taken-over subdomain attacks) .

To do sign the CSRF Token, set the property `micronaut.security.csrf.signature-key`.

[configuration]
----
micronaut:
  security:
    csrf:
      signature-key: pleaseChangeThisSecretForANewOnekoqQ-EstJQLr_T-1qS0gZH75aKtMN3Yj0iPS4hcgUuTwjAzZr1Z9CAow
----

The HMAC of a signed CSRF token binds the token to the session identifier resolved via api:security.session.SessionIdResolver[] (for example, the HTTP session id or the `jti` claim of a JWT) and to the name of the authenticated user. A token issued to one user, for example upon login, is therefore not valid for a request authenticated as another user, even if an attacker manages to write the token into the victim's CSRF cookie.

If you generate a CSRF token yourself with api:security.csrf.generator.CsrfTokenGenerator[], use `generateCsrfToken(request, authentication)` when the request does not carry the authentication yet, for example while handling a login. `generateCsrfToken(request)` binds the token to the user authenticated in the request, if any.

The bound name is `Authentication#getName()`, the canonical name of the principal. Attributes of the authentication are not used, because distinct principals may share attribute values: users validated via the UserInfo endpoint of several OpenID providers are named `<provider>:<sub>` and may share the raw `sub` or the `email` attribute, and they do not share CSRF tokens. The login handlers which issue a JWT (api:security.token.cookie.TokenCookieLoginHandler[] and api:security.oauth2.endpoint.token.response.IdTokenLoginHandler[]) supply the api:security.token.cookie.LoginCookieProvider[] beans with the authentication named as token based authentication names the user from the issued token: the value of the `micronaut.security.token.name-key` claim (default `sub`, which is the principal name), falling back to the principal name. The value computed at login therefore matches the one computed on later requests. Custom authentication mappers (for example a custom `OpenIdAuthenticationMapper#getUsername`) keep working as long as the issued token carries the name. A request authenticated without a name is treated like an anonymous one.
