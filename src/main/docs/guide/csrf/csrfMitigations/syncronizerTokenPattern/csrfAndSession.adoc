If you use <<session, Session-Based Authentication>> and Micronaut Security CSRF, a CSRF token is automatically generated upon login and saved into the HTTP Session. <<session, Micronaut Session>> provides an implementation
api:security.csrf.CsrfTokenRepository[] which fetches the CSRF token from the user's HTTP session. Thus, when the application sends new request to the sever with a CSRF token (e.g. in a hidden form field or HTTP Header), the server validates the supplied token against the value stored in the HTTP Session.

api:security.csrf.session.SessionCsrfTokenRepository[] takes precedence over api:security.csrf.repository.CookieCsrfTokenRepository[]. When a request carries an HTTP session which holds a CSRF token, the supplied token is only validated against the session token; a CSRF cookie present in the request is ignored. This prevents a CSRF cookie planted in the user's browser (for example, from a sibling subdomain) from replacing the token stored in the session.

You can disable the CSRF Session repository by setting `micronaut.security.csrf.repositories.session.enabled` to false.

The session is authoritative only when it holds a CSRF token. If a request carries an HTTP session without a CSRF token attribute (for example, a session created before CSRF was enabled or by a login path which does not run api:security.csrf.session.CsrfSessionPopulator[]), the next repository, such as api:security.csrf.repository.CookieCsrfTokenRepository[], is consulted and a planted CSRF cookie is not neutralized. Make sure every login path which creates a session runs api:security.csrf.session.CsrfSessionPopulator[]. The default api:security.session.SessionLoginHandler[] does. Setting `micronaut.security.csrf.signature-key` further limits this case: the HMAC binds the token to the session ID, so a token issued for another session is rejected even when only the cookie repository holds a token.

Repositories are consulted following their `getOrder()` and the first one holding a CSRF token wins. Custom api:security.csrf.repository.CsrfTokenRepository[] beans should declare an explicit `getOrder()`: at the default order of 0 they tie with api:security.csrf.repository.CookieCsrfTokenRepository[], and the order between tied repositories is then unspecified.
