The module evaluates its built-in rules in the same sequence as the https://web.dev/articles/fetch-metadata#enforcing_a_resource_isolation_policy[recommended resource isolation policy]:

. Requests without `Sec-Fetch-Site`
. Same-origin requests
. Same-site requests
. Requests initiated directly through browser UI
. Simple `GET` navigations
. Requests to https://docs.micronaut.io/latest/guide/#annotationBasedCors[CORS-enabled routes]

Unlike the reference policy, which allows same-site requests, the same-site rule is disabled by default: a same-site request can come from any subdomain of the site, including ones the application does not control. Enable it with `micronaut.security.fetch-metadata.rules.allow-same-site` when every same-site origin is trusted.

The first rule that returns `ALLOWED` or `REJECTED` decides the request. A rule returns `UNKNOWN` when it does not apply, allowing evaluation to continue. If every rule returns `UNKNOWN`, the filter responds with `403 Forbidden`. Rejections are logged at `DEBUG` level by `io.micronaut.security.fetchmetadata.FetchMetadataFilter`, together with the request's `Sec-Fetch-Site`, `Sec-Fetch-Mode`, and `Sec-Fetch-Dest` values.

Because the outcome depends on the Fetch Metadata request headers, the filter adds `Sec-Fetch-Site`, `Sec-Fetch-Mode`, and `Sec-Fetch-Dest` to the `Vary` header of the responses to the requests it evaluates, both allowed and rejected, merging them with any existing `Vary` values. This prevents a shared cache from serving a response allowed for a same-origin request to a cross-site request.

[cols="1,2,1,1"]
|===
|Rule |Behavior |Default |Order

|No Fetch Metadata
|Allows clients that do not send `Sec-Fetch-Site`. Requests with `Sec-Fetch-Site` are evaluated by the remaining rules even when another Fetch Metadata header is incomplete or unrecognized.
|Enabled
|100

|Same origin
|Allows `Sec-Fetch-Site: same-origin`.
|Enabled
|200

|Same site
|Allows `Sec-Fetch-Site: same-site`. Enable this only when every same-site origin is trusted.
|Disabled
|300

|Browser initiated
|Allows `Sec-Fetch-Site: none`, which represents requests explicitly initiated through browser UI, such as the address bar or a bookmark.
|Enabled
|400

|Simple navigation
|Allows `GET` requests with `Sec-Fetch-Mode: navigate`, except `object`, `embed`, and unrecognized destinations.
|Enabled
|500

|CORS endpoint
|Allows a request when the matched route declares CORS and its configuration accepts the request origin and method, and, for a request carrying a `Cookie` header, allows credentials.
|Enabled
|600
|===

The simple navigation rule intentionally allows cross-site `GET` navigations, including frame and iframe destinations. It does not protect against framing; use https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Content-Security-Policy/frame-ancestors[CSP `frame-ancestors`] and/or https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/X-Frame-Options[`X-Frame-Options`] to control whether the application may be framed.

The compatibility rule treats requests without `Sec-Fetch-Site` as Fetch Metadata-unaware. A request that includes `Sec-Fetch-Site` but has an incomplete or unrecognized Fetch Metadata value is evaluated by the remaining rules and is rejected if none allows it. Each rule relies only on the headers it inspects: the same-origin, same-site, and browser-initiated rules need a recognized `Sec-Fetch-Site`, while the simple navigation rule also needs a recognized `Sec-Fetch-Mode` and `Sec-Fetch-Dest`. A same-origin request whose `Sec-Fetch-Dest` is a value Micronaut does not know, such as the `websocket` destination some browsers send for WebSocket handshakes, is therefore still allowed. To reject requests without `Sec-Fetch-Site`, disable `micronaut.security.fetch-metadata.rules.allow-no-fetch-metadata`. Verify that every supported browser, API client, webhook, monitoring probe, and other caller sends `Sec-Fetch-Site` or is otherwise exempted before enabling this stricter behavior.

[configuration]
----
micronaut:
  security:
    fetch-metadata:
      rules:
        allow-no-fetch-metadata: false
----

NOTE: Browsers only send Fetch Metadata headers to https://w3c.github.io/webappsec-secure-contexts/#potentially-trustworthy-origin[potentially trustworthy origins], such as HTTPS origins and `localhost`. An application served over plain HTTP to other hosts receives no `Sec-Fetch-*` headers, so with the default configuration every such request is allowed by the compatibility rule, and with `allow-no-fetch-metadata: false` every such request is rejected. Serve the application over HTTPS to benefit from this module.
