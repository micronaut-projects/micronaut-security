To exempt another deliberately public resource or implement an application-specific policy, provide a `@Singleton` implementation of api:security.fetchmetadata.HttpRequestFetchMetadataRule[]. For example, this rule allows a fixed public resource path:

snippet::io.micronaut.security.docs.fetchmetadata.PublicResourceFetchMetadataRule[tags="imports,clazz"]

A custom rule should return api:security.fetchmetadata.FetchMetadataRuleResult#UNKNOWN[UNKNOWN] when it does not apply. Rules run on the request thread, usually a Netty event loop, for every request the filter evaluates: keep them fast and never perform blocking I/O, such as a database or HTTP call, in a rule. Returning `ALLOWED` or `REJECTED` stops rule evaluation. Because api:security.fetchmetadata.FetchMetadataRule[] implements `Ordered`, override `getOrder()` when the rule must run at a particular stage. Lower order values execute first. If you do not override `getOrder()`, the rule has order `0` and runs before every built-in rule. A rule that returns `REJECTED` at that position also applies to requests without Fetch Metadata, such as API clients. The built-in rules use the order values listed in the <<fetchMetadataResourceIsolationPolicy,resource isolation policy>> table, spaced so that a custom rule can run between two of them; the example deliberately runs before every built-in rule.

CAUTION: Keep exemptions narrow and based on server-controlled information such as an exact route or resource identifier. Do not exempt a path containing authenticated or user-specific data solely because it is publicly reachable.
