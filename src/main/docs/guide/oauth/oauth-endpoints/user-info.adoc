Micronaut Security OAuth2 registers a bean of type api:io.micronaut.security.token.validator.TokenValidator[] for each OpenID provider.
It provides token validation using the remote authorization server's
https://openid.net/specs/openid-connect-core-1_0.html#UserInfo[`UserInfo` endpoint].

image::userinfo.svg[]

The `UserInfo` endpoint URL is obtained automatically from the authorization server's metadata (obtained by visiting the `.well-known/openid-configuration` endpoint of the authorization server).

However, you can set it also via configuration:

include::{includedir}configurationProperties/io.micronaut.security.oauth2.configuration.OauthClientConfigurationProperties$OpenIdClientConfigurationProperties$UserInfoEndpointConfigurationProperties.adoc[]

NOTE: Set `micronaut.security.oauth2.userinfo.validator` to `false` to disable `UserInfo` endpoint token validation.

=== Which provider receives the token

A bearer token is only sent to the `UserInfo` endpoint of the provider which issued it, so that an access token issued by one provider is never disclosed to another provider:

- If the token is a JWT, its `iss` claim must be equal to the expected issuer of the provider: `micronaut.security.oauth2.clients.*.openid.issuer-identifier` if set, otherwise `micronaut.security.oauth2.clients.*.openid.issuer`. The issuer announced by the discovery document is only used when neither is configured, since a provider must not be able to claim the issuer of another provider. The comparison is exact and tolerates only the case of the scheme and a trailing slash, the same rule api:security.oauth2.client.IdTokenClaimsValidator[] applies. The `iss` claim is read without verifying the token, which is left to the provider. A JWT issued by somebody else is never sent to the `UserInfo` endpoint, not even when only one provider is configured.
- If several providers expect the same issuer but have distinct `UserInfo` endpoints (for example two Oracle IDCS tenants, which both issue tokens with the provider wide issuer `https://identity.oraclecloud.com/`), a JWT of that issuer cannot be attributed to one of them. It is handled like an opaque token: sent only to the providers which opt in with `validate-opaque-tokens: true`. A warning naming the providers is logged the first time such a token is checked.
- If no issuer is known for a provider (neither configured nor announced by its discovery document, for example with `fetch-configuration: false` and a manually configured `user-info.url`), its validator cannot tell its own JWTs apart from those of other issuers and treats every JWT like an opaque token. A warning is logged at startup; configure `openid.issuer` or `openid.issuer-identifier` to bind the endpoint to an issuer.
- If the token cannot be attributed to a provider (an opaque token, an encrypted JWT, or a JWT without an `iss` claim), it is sent to the `UserInfo` endpoint only when that provider is the only one known to the application (the only enabled OpenID client configured under `micronaut.security.oauth2.clients` and the only api:security.oauth2.endpoint.userinfo.UserInfoClientTokenValidatorConfiguration[] bean, counted together by name), or when the provider explicitly opts in with `micronaut.security.oauth2.clients.*.openid.user-info.validate-opaque-tokens: true`. Set the property to `false` to never send such tokens to a provider. The implicit allowance depends on the configured clients, not on which of them were reachable at startup: a provider whose discovery document could not be fetched still counts, so a temporary outage of one provider never routes its tokens to another. A JWT of an issuer shared by several providers is never covered by this implicit allowance; it always requires the explicit opt-in.

WARNING: Enabling `validate-opaque-tokens` for several providers sends every opaque token to each of them. Only do so if you trust every one of those providers with the tokens of the others.

If you register api:security.oauth2.endpoint.userinfo.UserInfoClientTokenValidatorConfiguration[] beans yourself, set `issuer` and, if needed, `validateOpaqueTokens` on the builder to get the same behavior.

=== Provider binding

The api:security.authentication.Authentication[] created from a `UserInfo` response is bound to the provider whose `UserInfo` endpoint answered:

- The attribute `oauth2Provider` (api:security.oauth2.endpoint.token.response.OauthAuthenticationMapper[]`.PROVIDER_KEY`) is always set to the provider name. A value with that key in the `UserInfo` response is ignored, so api:security.oauth2.ProviderResolver[] always resolves the provider which validated the token.
- The username returned by `Authentication.getName()` is qualified with the provider name, followed by `:` and the `sub` claim, for example `okta:248289761001`, when `micronaut.security.oauth2.openid.qualify-username-with-provider` is `true`. If the property is not set, the username is qualified when more than one enabled OAuth 2.0 client, other than client-credentials-only clients, is configured under `micronaut.security.oauth2.clients`. The `sub` attribute still holds the unqualified subject. Set the property explicitly if your application keys data on the name, so adding an unrelated client later does not rename every user. The default api:security.oauth2.endpoint.token.response.OpenIdAuthenticationMapper[] used at login applies the same rule and the same property, so a user has the same name in a browser login and in a bearer request. See <<openid-user-details, User Details Mapping>>.
- Client names under `micronaut.security.oauth2.clients` must not contain `:`. Such a name is not supported by the configuration binding, and the `UserInfo` validator additionally rejects it with a `ConfigurationException` when usernames are qualified, because the provider `alpha` with the subject `beta:victim` and the provider `alpha:beta` with the subject `victim` would both be named `alpha:beta:victim`. The `sub` claim may contain `:`, since the provider name is everything before the first `:` of a qualified name.

A subject is only unique within its issuer. Without this binding, whoever controls one configured provider could answer a `UserInfo` request with the subject of a user at another configured provider and your application would treat the request as coming from that user.

NOTE: Only the identity is bound to the provider. Roles are still resolved from the attributes of the `UserInfo` response (for example by api:security.token.DefaultRolesFinder[] reading the `roles` claim), so a provider you configure is trusted to state the roles of its own users. Only configure providers you trust, and use `micronaut.security.token.roles-name` or a custom api:security.token.RolesFinder[] if the claim is not appropriate for a provider.
