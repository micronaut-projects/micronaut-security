Part of the OpenID Connect specification includes a draft document titled https://openid.net/specs/openid-connect-session-1_0.html[Session Management]. Because the specification is a draft, some providers have implemented it differently or not at all. See the following diagram for how end session works with default configuration:

image::openid-end-session.svg[]

If any configured OpenID provider supports end session behavior, a route will be registered that responds to `/oauth/logout` and redirects to the provider to log the user out. A parameter is also sent to the provider that indicates what URL the provider should redirect the user to after logging out. The default URL is `/logout` which will cause the local authentication to also be cleared and a final redirect issued according to the api:security.handlers.LogoutHandler[].

The end session URL advertised by the provider (the `end_session_endpoint` of its discovery document, or the URL derived from the issuer for providers that do not advertise one) is used as an opaque URI: the logout parameters, such as `post_logout_redirect_uri` or `id_token_hint`, are percent-encoded and appended to its query component, and any query component already present in the provider URL is preserved. The provider URL is never expanded as a URI template. The provider URL must be an absolute `http` or `https` URL with a host and without user information. If it is empty, takes another form (a relative URL, another scheme, or `https://user:password@provider.example/logout`) or is not a valid URI, no redirect is issued and `/oauth/logout` responds with 404.

To enable the usage of the `/logout` endpoint, see the section on the <<logout, Logout Endpoint>>.

IMPORTANT: The `get-allowed` configuration option must be set to `true` because the OpenID provider will issue a redirect which is a GET request.

This library supports end session for Auth0, AWS Cognito, and Okta out of the box. The api:security.oauth2.endpoint.endsession.request.EndSessionEndpointResolver[] is responsible for determining which api:security.oauth2.endpoint.endsession.request.EndSessionEndpoint[] will be used for a given provider, if any.

For Okta and Oracle Cloud, api:security.oauth2.endpoint.endsession.request.OktaEndSessionEndpoint[] sends an `id_token_hint` parameter. It is the ID token obtained during the authorization code flow when that token is available in the authentication attributes. Otherwise, when `micronaut.security.authentication` is set to `idtoken`, it is the token which authenticated the current request, that is, the ID token cookie. Other tokens present in the request, such as an `Authorization` header added by a gateway or reverse proxy, are never sent to the OpenID provider.

Before choosing any of the default providers, the endpoint resolver will first look for an api:security.oauth2.endpoint.endsession.request.EndSessionEndpoint[] bean with a named qualifier that matches the name of the client in configuration. If no bean is found then the default endpoints will be matched against the issuer URL.

When several OpenID clients are configured, the `/oauth/logout` route has to decide which provider to redirect the user to. The api:security.oauth2.ProviderResolver[] (by default api:security.oauth2.DefaultProviderResolver[]) uses the provider name stored in the authentication attributes when the user logged in through the authorization code flow. With `micronaut.security.authentication=idtoken` the attributes of the authentication are the claims of the ID token which authenticated the request; api:security.oauth2.client.IdTokenClaimsValidator[] rejects tokens carrying an `oauth2Provider` or `openIdToken` claim, since those names are reserved for attributes set by the application, so the provider is resolved from the token claims. In that case, it compares the `iss` claim with the expected issuer of each enabled OpenID client (`micronaut.security.oauth2.clients.*.openid.issuer-identifier` if set, otherwise `openid.issuer`), tolerating only the case of the scheme and a trailing slash. If the `iss` claim matches more than one client (two Oracle Cloud identity domains, whose ID tokens share the issuer `https://identity.oraclecloud.com/` configured as their `issuer-identifier`, is a common example), the `aud` claim, and for multi-audience tokens the `azp` claim, must identify exactly one client by its `client-id`. When no single client can be determined no redirect is issued, so the ID token is never sent as `id_token_hint` to another provider's end session endpoint.
