The resource owner password credentials grant is described in https://tools.ietf.org/html/rfc6749#section-4.3[RFC 6749]. In short, credentials are passed directly to the token endpoint and if authentication succeeds, the token endpoint responds with the appropriate token.

The process that handles the token response onward is the same for both authorization code and password grants. See the following high level flow diagrams:

In Micronaut, the password grant is supported by setting the `grant-type` configuration option in the client configuration. For example:

[configuration]
----
micronaut:
  security:
    oauth2:
      clients:
        github:
          grant-type: password
----

NOTE: This example above is not intended to be a complete configuration reference

When a client is configured for the password grant type, the authorization code endpoints will not be available and instead an api:security.authentication.AuthenticationProvider[] will be created that will participate in the <<login,normal login flow>>.

For an OpenID provider, the ID token returned by the token endpoint is mapped to an api:security.authentication.Authentication[] with the same api:security.oauth2.endpoint.token.response.OpenIdAuthenticationMapper[] the authorization code flow uses: a mapper registered with a named qualifier matching the client name takes precedence, otherwise the global mapper, the one without a qualifier, is used. A mapper registered for another client is never used; if neither exists, the password grant of the client is disabled. See <<openid-user-details, OpenID Authentication Mapper>>. A user the mapper rejects cannot log in through the password grant, and the name, roles and attributes the mapper assigns are those of the resulting authentication.

If the token endpoint rejects the credentials with a 4xx response, such as `invalid_grant` for a wrong password, the provider answers with an authentication failure and the login is rejected with `401 Unauthorized`; the body of the response is the same for every rejection, while the reason of the api:security.event.LoginFailedEvent[] is `CREDENTIALS_DO_NOT_MATCH` for `invalid_grant` and `UNKNOWN` otherwise. A 5xx response or a connection failure is propagated as an error instead, since it is a malfunction of the provider rather than a verdict on the credentials, and so are the 4xx responses which are not one: a `408`, `425` or `429` response or an error code of `temporarily_unavailable` or `server_error`, with which some providers signal a transient condition, and an error code of `invalid_client`, `unauthorized_client`, `unsupported_grant_type` or `invalid_request` or a status of `404`, `405`, `407` or `415`, which rejects the client or the request rather than the user and is logged at `WARN` since it points at the client configuration.
